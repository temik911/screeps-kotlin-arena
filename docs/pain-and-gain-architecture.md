## 1. Зачем

Три боли оператора:

1. чтобы что-то улучшить, нужную строку приходится искать в большом объёме ветвлений;
2. часть строк в живых играх оказывается недостижимой, и узнаётся это случайно;
3. код продублирован: одно место обновили, второе забыли.

**Корень один.** Решения записаны как поток управления внутри нескольких функций по 700+ строк, а у ветки нет ни
имени, ни счётчика, ни единственного места:

- нет имени → нет адреса: лог говорит `why=kite`, а условие ступени собрано из предикатов, разбросанных на 400 строк
  выше, и каждое имя в нём приходит из одной из четырёх областей видимости;
- нет счётчика → недостижимость не видна: прибор `rung` считает только победившую ступень, а условия внутри ступеней,
  проходы командира и ветки стратега не считает никто;
- нет общего словаря → каждая ветка заново выписывает «чистый мили», «лекарь», «ключ клетки», и написания расходятся.

Предмет плана — дать каждому решению **имя, которое служит адресом, и счётчик, который приходит вместе с именем**,
не меняя поведения бота ни на один интент.

### 2.2. Недостижимое

**На уровне ступеней мёртвого нет.** По итоговой строке `rung t=` каждого из 20 живых матчей (счётчики
накопительные, поэтому берётся последняя строка матча, а не сумма строк):

- все 27 тегов лестницы срабатывали; редкие: `grab` 0,01 % крипо-тиков (7 матчей из 20), `chase` 0,03 % (5), `wall`
  0,04 % (10), `regroup` 0,04 % (15), `slotHold` 0,05 % (18);
- шаги: восемь из девяти; **`immobile` — 0 из 20**;
- проходы командира: `straggler` — 1 матч из 20, `catchall` 0,01 % (10), `pinned` 0,09 % (15);
- верх лестницы — `order` 30 %, `post` 23 %, `healMateOut` 15 %, `kite` 12 %.

Значит недостижимое сидит **ниже** уровня, на котором стоит прибор: в условиях ступеней (длинные цепочки `&&`), в
теле `commandFight`, в `armyStrategy`, где счётчиков нет вовсе. Прибор, который видит этот уровень, существует и
бота не трогает — покрытие V8 на стенде, переведённое через source map в строки Kotlin (прототип — приложение А).
На трёх синтетических сценариях: из 6 542 строк кода пакета **423 (6,5 %) не исполнены ни разу и ещё 769 (11,8 %)
исполнены не целиком** — строка выполнялась, но какая-то ветка внутри неё (`&&`, `?:`, лямбда) — никогда. По
функциям: `commandFight` 37 строк из 415, `creepTurn` 17 из 359, `armyStrategy` 16 из 347, `captureAllowed` 4 из
72. На полном гейте числа сожмутся; остаток — список кандидатов.

⚠️ **Оговорка к этим числам, найденная уже после замера.** Предохранители CPU (`CPU_GUARD_MS = 50`, `Tuning.kt:667`)
читают настоящее время и на стенде (`game/utils.mjs:12` — `process.hrtime`), а под сбором покрытия Node медленнее:
в трёх прогонах предохранители сработали **255 раз** (строки `cpu t=N guard: …`), тогда как в 270 логах обычного
гейта — ни разу. Значит, под покрытием бот вёл себя иначе, чем в гейте (командир пропускал перебор), и цифры выше
занижают покрытие ровно тех путей, которые предохранитель отключает. Сам прибор от этого не хуже, но запускать его
надо с выключенными часами стенда — это пункт этапа 0.

⚠️ **«Не встретилось» — не «недостижимо».** `immobile` за 20 матчей не сработал ни разу, но крип без живых `MOVE`
возможен, и `creepTurn` зовётся для всей армии (`PainAndGain.kt:597`) — это редкость, а не мёртвый код. `grab`
срабатывает раз на десять тысяч крипо-тиков и может решить матч. Порог «N матчей без срабатывания» был бы числом
**названным**, а не вычисленным: удаляется только **доказанно** перекрытое (этап 7).

## 3. Правила этого захода

Прошлая переработка дала урок, и он записан в её же разделе 11: **ни один шаг под тождеством отвергнут не был**
(v236–v239, v241, v248, v251–v252, v255–v263), **а все четыре отказа живого A/B — v242, v244, v246, v253 — шаги, где
новая форма приезжала вместе с новым поведением** (постановка как решатель, `threatAt` заменой и добавочным термом
с назначением огня отрядом, спасение первым в очереди арбитра). Поведенческие шаги проходили тоже (v240, v249,
v250), но каждый платил циклом A/B, и отказ уносил форму вместе с поведением: термы, единая модель строя и
`Disposition` не сделаны не потому, что форма плоха, а потому, что A/B судил поведение, с которым она пришла.

1. **Ни один шаг этого плана не меняет поведение.** Каждый коммит проходит оракул тождества (раздел 6). Шаг, который
   тождество не проходит, не «почти готов» — он содержит ошибку переноса.
2. **Механика и поведение не делят коммит и версию.** Пока план исполняется, поведенческих правок в пакете нет
   вовсе (раздел 7); они возвращаются после него и обходятся дешевле.
3. **Сила оракула известна построчно.** Перед переносом функции снимается покрытие гейта по ней (этап 0): строка,
   которую гейт не исполняет, тождеством не проверена. Для неё — сценарий, который её достаёт (ghost записанного
   матча). Если сценария нет — перенос читает **второй агент** (решение оператора 13): свежий субагент без
   контекста автора, которому даны старый текст, новый текст и один вопрос — «где перенос меняет поведение»; его
   ответ цитируется в абзаце версии. Такая строка в абзаце версии названа «проверена чтением, стендом не
   исполняется» — объявить её проверенной тождеством нельзя, и итоговая живая проверка (6.4) смотрит на неё первой.
4. **Различие, найденное при сведении написаний, не сглаживается.** Написания А и Б «чистого мили» получают **разные
   имена** и остаются каждое на своём месте; сведение их к одному — поведенческое решение, отдельная версия.
5. **Критерии приёмки структурные, а не числовые.** «Функция не длиннее N строк» — число названное. Критерий — то,
   что можно проверить `grep`-ом, компилятором или прибором этапа 0: «написание встречается в одном месте»,
   «порядок ступеней читается из одного списка», «ребра вверх нет». Числа раздела 2 — снимок, с которым сравнивают.
6. **Правило держит форма, а не память.** Каждое «так больше не пишем» приходит вместе с проверкой в гейте
   (линт написаний, гейт графа), иначе через двадцать версий оно нарушено.
7. **Путь — перекройка по швам** (решение оператора 13.09.2026, остаётся в силе): не новый бот рядом.

## 4. Целевая форма

Конвейер стадий остаётся тем же. Меняется то, **чем записано решение внутри стадии**.

### 4.1. Словарь фактов — `Unit`

Факты о крипе считаются один раз за тик в `buildWorld` и читаются по имени. Это `class Unit` из раздела 3
`pain-and-gain-rework.md`, который тогда не был сделан:

```kotlin
internal class Unit(val creep: Creep) {          // строится в buildWorld для своих и чужих, живёт один тик
    val key: Int                                  // x * 100 + y
    val liveMelee: Boolean; val liveRanged: Boolean; val liveHeal: Boolean   // живая часть
    val bornMelee: Boolean                        // часть ATTACK в теле, живая или нет (сегодняшний isMelee)
    val armed: Boolean                            // liveMelee || liveRanged (сегодняшний hasWeapon)
    val healerOnly: Boolean                       // !armed && liveHeal
    val stripped: Boolean                         // !armed && !liveHeal (сегодня wounded и stripped)
    val meleeOnlyBorn: Boolean                    // написание А
    val meleeOnlyLive: Boolean                    // написания Б и В
}
```

Список полей — **инвентарь из кода, а не из этого файла**: исполнитель снимает `grep`-ом все написания ролевых
тестов и выборок (раздел 2.3 — начало списка) и даёт имя каждому различимому варианту. Сегодняшние
`hasMelee(creep)` и родня остаются как тонкие обёртки над `Unit`, пока последний вызов не переведён. Ключ клетки —
`inline fun key(x: Int, y: Int)` и `inline val Creep.key` / `Position.key`: инлайн даёт тот же скомпилированный код.
Группы постур — свойство перечисления (`Posture.withdrawing`).

### 4.2. Защёлка — `Latch`

Гистерезис «вошёл по одному условию, вышел по другому» выписан руками минимум пять раз (`rotatingIds`,
`aggressiveIds`, `engagingIds`, `rallyingIds`, `impatientIds`). Один примитив:

```kotlin
internal class Latch(private val ids: MutableSet<String>) {     // ids остаётся полем Memory — см. ловушку AbortRepair
    fun update(id: String, enter: Boolean, exit: Boolean): Boolean   // состояние после обновления
    operator fun contains(id: String) = id in ids
}
```

Запись в память перестаёт прятаться внутри `val x = … run { … Memory.add … }` и становится оператором на том же
месте последовательности.

### 4.3. Таблица решений и обходчик

Цепочка «первое сработавшее условие выигрывает» записывается списком именованных строк. Лестница хода:

```kotlin
internal class Aim(val target: Position, val standoff: Int, val avoid: Boolean = false, val nearFlow: Boolean = false)
internal class Rung(val tag: String, val guard: Turn.() -> Boolean, val aim: Turn.() -> Aim)

private val LADDER by lazy { listOf(                        // порядок списка = приоритет; другого описания нет
    Rung("keeper",   { keeper },   { Aim(here, 0) }),
    Rung("slotHold", { slotHold }, { Aim(here, 0) }),
    // …
    Rung("post",     { true },     { Aim(post, POST_STANDOFF, avoid = true) }),
) }
```

`Turn` — объект фактов одного хода: те самые ~60 величин `:294–690`, но полями с именами, каждая определена один
раз, рядом со своим комментарием-вердиктом. Обходчик один на все таблицы и делает три вещи: выбирает первую строку с
истинным условием (семантика сегодняшнего `when`), считает, печатает причину. Счётчики на строку:

- `won` — строка выиграла (сегодняшний `rungCount`, печать `rung t=` не меняется);
- `true` — условие было истинно;
- `shadowed = true − won` — условие истинно, но выше стояла другая. Строка с `true > 0` и `won = 0` недостижима
  **из-за порядка** — ровно тот дефект, что в v235 искали руками («назначение лекаря исполнялось 25–40 % тиков,
  потому что выше стояли `order`, `kite` и `wall`»);
- `true = 0` на всём гейте и всех живых сериях — условие ни разу не было истинно.

Проверка всех условий, а не только до первого истинного, возможна потому, что ингредиенты условий уже посчитаны в
`Turn`, а сами условия после этапа 2 — чистые чтения. **Полный обход включён в живой сборке** (решение оператора
8): недостижимость, ради которой всё затеяно, видна только живьём, стенд командира почти не экспонирует. Цена —
десятки булевых чтений на крипа за тик; она входит в итоговый замер CPU (6.3). Полный обход стоит за одной
константой сборки — не как тумблер поведения (на интенты он не влияет), а как рубильник: если итоговый замер
покажет перерасход, выключение решает оператор, и для него не нужна правка кода.

Счётчики накопительные и печатаются отдельной строкой прибора с той же периодичностью и в том же виде `k=v`, что
уже принят для `rung t=`; по хранилищу матчей их сводит новый срез `tools/series.py` (строки с `true = 0`; строки с
`true > 0` и `won = 0`; доля перекрытия по строкам) — он и даёт кандидатов этапа 7.

Тот же обходчик — для цепочки шага (9 строк), проходов `commandFight` (`Pass(tag, run)`), ворот `captureAllowed`
(`Gate(tag, verdict)`, вердикт — `Allow | Veto(reason) | Next`) и правил постуры в `armyStrategy`, где они
оказываются цепочкой.

### 4.4. Носитель вместо замыкания

Функция-замыкание с сорока общими локальными (`commandFight`, `armyStrategy`) становится классом одного вызова:
локальные — поля в прежнем порядке, локальные функции — методы, проходы — методы `passRetreat()`, …, собранные в
таблицу. Оценки `scoreMelee` / `scoreRanged` / `scoreHeal` остаются функциями как есть: клетка как argmax списка
термов — смена поведения, дважды отвергнутая живьём, и в этот план не входит.

### 4.5. Контракты стадий без сантехники

Классы `<Сегмент>In` исчезают (решение оператора 5: действующее правило «Как менять» — «оркестровка распаковывает
выход в локальные с прежними именами» — отменено). Стадия получает параметрами **выходы предыдущих стадий
целиком**:

```kotlin
val m = armyMeasures(ctx, base)
val s = armyStrategy(ctx, base, m)
val g = armyTargets(ctx, base, m, s)
```

Поле объявляется один раз — в `Out` стадии-владельца. Порядок конвейера проверяет компилятор: стадия не может
прочитать выход более поздней, потому что он ей не передан. `runArmy` сжимается до списка вызовов; `ArmyTick`
перестаёт быть четвёртой копией тех же имён и держит ссылки на выходы.

### 4.6. Правило зависимостей

Уровни объявляются файлом рядом со стендом и проверяются гейтом по скомпилированным модулям. Таблица ниже
**принята оператором как стартовая** (решение 6) и с этапа 0 лежит в `levels.txt`; на этапе 5 исполнитель
пересматривает её по фактическому графу, и любое отличие от этой таблицы возвращается оператору находкой, а не
правится молча:

| уровень | файлы |
|---|---|
| 0 | `Rules`, `Tuning`, типы-перечисления (`Posture` и родня переезжают сюда) |
| 1 | `Memory`, `DistanceMap`, `InfluenceMap`, модель мощи (`ourPowerOf` / `enemyPowerOf` / `fightTicks` — чистые функции, сегодня в `Forecast.kt`) |
| 2 | `World` |
| 3 | `Forecast` (прокат), `Strategist`, `Missions` |
| 4 | `Tactician`, `Fight`, `Formation` |
| 5 | `Arbiter`, `TrafficManager` |
| 6 | `Executor` |
| 7 | `PainAndGain` (оркестровка), `AbortRepair` |
| вне уровней | `Instruments` — читает всех, **его не импортирует никто**, кроме оркестратора |

Зависимость направлена вниз или внутри уровня. Решение прошлого тика читается явно (`Memory.prevPosture`), а не
полем объекта, про которое надо знать, что стратег его ещё не переписал.

### 4.7. Счётчик живёт у того, кто считает

Счётчик объявляется в файле стадии, которая его наращивает; `Instruments` его читает и печатает. Текст строк не
меняется. Действующее правило раздела «Архитектура» («счётчик, который только печатается, — в `Instruments.kt`»)
**отменено оператором** (решение 4) — основание: 431 символ из 650 в графе идёт в `Instruments`, и пока это так,
цикл на 11 файлов не разрезать. Форматы печати не нормализуются: составные
поля (`capgate=a/b`, сортированные словари) остаются как есть, иначе теряется тождество логов и сопоставимость
`series.py` со старыми версиями.

## 5. Этапы

План отдан исполнителю целиком (решение оператора 3); порядок этапов — 0 → 1 → 2 → 3 → 4 → 5 → 6, этап 7 идёт
рядом начиная с конца этапа 3. Каждый этап — серия мелких коммитов, каждый проходит оракул (раздел 6). Посадка —
по правилу пачки из `CLAUDE.md`, не реже одной на этап, с тегом `pain-and-gain-vN`: теги этапов — точки, по которым
ищется виновный, если итоговая живая проверка (6.3, 6.4) что-то найдёт. Инструменты под `tools/` — отдельными
коммитами и в `main` сразу. Живых игр до конца плана нет (решения 11 и 12).

### Этап 1. Словарь фактов

**Что делается.** Инвентарь написаний (`grep`, раздел 2.3 — начало) → `Unit` и `key` → замена написаний по одному
понятию на коммит → каждое заменённое написание уходит в `lint.py`. Обёртки `hasMelee(creep)` и родня читают
`Unit`; когда вызовов не осталось — удаляются. Дословно повторённые выборки (25 выражений, 53 вхождения) становятся
именованными полями `Ctx` или выхода стадии, которая владеет списком.

**Чего не делается.** Написания А и Б не сводятся к одному (правило 3.4, подтверждено решением оператора 9).
Вместо этого в `docs/pain-and-gain.md` кладётся таблица «место → какое написание → что это значит для мили с
выбитым оружием» — 27 мест, где различие либо намеренно, либо нет. Таблица **возвращается оператору находкой** сразу
после этапа; сведение написаний — поведенческая версия после плана, по его слову.

**Ловушки.**

- Кэш фактов на тик корректен, только если тело крипа не меняется внутри нашего `loop()`. Единственный писатель API —
  `Executor` в конце тика, так что это верно; проверить, что `Forecast.simulate` работает на своих профилях, а не
  правит `creep.body`.
- Кэш строится заново каждый тик и держится в `Ctx`, а не в объекте-синглтоне: таблица в синглтоне вне списка
  владельцев `AbortRepair` повторяет дефект v222.
- `value class Cell(val k: Int)` **не вводить**: в Kotlin/JS значение упаковывается в объект, когда попадает в
  обобщённую коллекцию (`HashMap<Cell, …>`, `HashSet<Cell>`), а ключи клеток живут именно там. Только `inline fun` и,
  если хочется имени типа, `typealias`.

**Оракул.** Тождество. **Приёмка.** Каждое написание из инвентаря встречается в коде ровно в одном месте — в
определении (проверяет `lint.py`); `wounded` и `stripped` — одно имя; таблица А/Б передана оператору.

### Этап 2. Побочные эффекты — операторами, защёлки — примитивом

**Что делается.** В `creepTurn` (`:311–313`, `:362`, `:488`, `:671–673`, `:852–853`) и везде, где `grep` находит
тот же рисунок (`if (…) Memory.X.add(id) else Memory.X.remove(id)`), запись выносится из выражения в оператор **на
том же месте последовательности** и идёт через `Latch`. Счётчики приборов, зашитые в выражения (`rotOut++` внутри
`run { }`), — тоже операторами.

**Чего не делается.** Записи **не переезжают** в «фазу обновления» в конце хода: между записью и концом хода стоят
чтения той же таблицы (`Memory.rotatingIds` читает `Formation.kt:428`, `:461`), и перенос меняет, что они увидят.
Сдвиг записи допустим только там, где перечислены все читатели таблицы и показано, что между старым и новым местом
их нет.

**Ловушка.** `AbortRepair.repairFields` обходит поля объекта-владельца и чинит только `MutableMap` и `MutableSet`
(`AbortRepair.kt:25–58`), вглубь идёт только по значениям словарей. Коллекция, спрятанная внутрь `Latch`, выпадает
из починки. Поэтому множества остаются полями `Memory`, а `Latch` — вид поверх них.

**Оракул.** Тождество. **Приёмка.** В теле `creepTurn` и `commandFight` нет записи в `Memory` и нет `++` внутри
выражения `val … =`; линт ловит рисунок `if (…) Memory.…add(…) else Memory.…remove(…)` вне `Latch`.

**Ловушки.**

- **Затенение имён — главная.** Условия — лямбды с получателем `Turn`, внутри которого виден `ArmyTick`, а снаружи —

  До переноса — проверка: множества имён `Turn`, `ArmyTick`, `Ctx` и членов `PainAndGain` попарно не пересекаются;
  она остаётся в `lint.py`.
- Таблица собирается **внутри функции или `by lazy`**, не инициализатором верхнего уровня, который трогает другой

- Порядок инициализации полей класса — порядок текста. Поле, читающее другое поле ниже по тексту, получит `null` /

- `run { … return@run … }` внутри предикатов (`:576`, `:589`, `:844`) при переносе в функцию превращается в обычный
  `return` — проверить каждое.

**Оракул.** Тождество **плюс** карта этапа 0: для строк `creepTurn`, которых гейт не исполняет, — ghost-сценарий из
живого матча, где ступень срабатывала (`chase`, `grab`, `wall` — матчи есть в хранилище, счётчик `rung` говорит
какие), либо чтение вторым агентом по правилу 3.3.

**Приёмка.** В `Tactician.kt` порядок ступеней читается из одного списка, и другого места, задающего приоритет,
нет. У каждого предиката одно определение. Тег из лога находится `grep`-ом в одной строке таблицы, и условие с
действием стоят в ней же. Прибор печатает `won` / `true` / `shadowed` по всем 27 + 9 строкам. В абзац версии
записан след CPU стенда до и после этапа (6.3).

### Этап 4. `commandFight`, `captureAllowed`, `armyStrategy`

**Метод один на все три функции** — тот, которым был написан раздел 7 прошлого плана:

1. **карта секций** функции (диапазон строк → что решает → какие локальные читает и пишет → какие счётчики и память
   трогает) — кладётся в `docs/` до первой правки;
2. **носитель** (4.4): локальные → поля в прежнем порядке, локальные функции → методы; ранние выходы (`Fight.kt:436`,
   `:448`) остаются до построения носителя;
3. секции → методы в прежнем порядке вызова;
4. там, где секция — цепочка «первый сработавший», она становится таблицей под общим обходчиком: девять проходов
   `commandFight` (включая безымянные вставки `:987`, `:1123` — они получают имя), ворота `captureAllowed`.

Для `captureAllowed`: счётчики между воротами (`capOffered++` `:246`, `kvetoAll++` `:293`) — часть своей строки
таблицы и исполняются в том же порядке. Для `armyStrategy` исполнитель сначала пишет карту секций и по ней решает,
где цепочка, а где последовательность; таблица ради таблицы не нужна.

**Ловушки.** Те же, что на этапе 3, плюс: замыкания держат `var`, которые меняются позже (`passTag`, `maxV`), — они
становятся `var`-полями; `place(... depth)` рекурсивна и считает `passCount` только при `depth == 0` (`:662`).

**Оракул — здесь он слабее всего.** По `exposure.py` (замер 11.09.2026) командир правит боем 0,4 % тиков стенда
против 2,3 % живьём. Поэтому карта этапа 0 по `commandFight` обязательна **до** первой правки, и недостающее
добирается ghost-сценариями живых боёв — записей в `~/ScreepsArena/replays/` достаточно, чтобы выбрать матчи, где
командир работал долго. Что не достали и они — читает второй агент (3.3). Живых игр на этом этапе нет (решения
оператора 11 и 12); распределение приборов `pass` / `cmdwhy` против контрольной версии сверяется в итоговой
проверке (6.4), и строки, помеченные «стендом не исполняется», там смотрятся первыми.

**Приёмка.** В трёх функциях не осталось замыканий над общими локальными; порядок проходов и порядок ворот читаются
из одного списка каждый; все проходы имеют имя и счётчик; карты секций лежат в `docs/`.

### Этап 5. Контракты стадий и направление зависимостей

**Что делается.**

1. 13 пар `In` / `Out` — **по одной стадии на коммит**: `In` исчезает, тело стадии читает `m.contact` вместо
   `contact`. Замена механическая (имена полей внутри одного `Out` уникальны), объём большой — сотни ссылок.
2. `runArmy` и `tickBody` — список вызовов; `ArmyTick` держит ссылки на выходы, а не копии полей.
3. Рёбра вверх раздела 2.5, по одному на коммит:
   - `updateKeepers` — первый оператор `armyMeasures` (`World.kt:615`); вызов переезжает в `runArmy`
     непосредственно перед `armyMeasures`. Проверить, что до него в `armyMeasures` ничего не исполняется;
   - `heldFlag` / `guardFlag` — факты о флагах → в `World.kt`;
   - `ourPowerOf` / `enemyPowerOf` / `fightTicks` — чистая модель → отдельный файл уровня 1;
   - `Posture`, `CmdMode`, `Intent` — типы → уровень 0; чтения постуры в `World` — через `Memory.prevPosture` с тем же
     значением;
   - `sym`, `mirrorTL` → туда, где живёт геометрия карты (уровень 1);
   - `PainAndGain_getInstance` в `Forecast` и `Formation` — нужная величина приходит параметром.
4. `levels.txt` пустеет по мере снятия рёбер.

**Ловушка.** Граф снимается со скомпилированных модулей, то есть **после инлайна**: `inline fun` переносит ребро
из файла-определения в файл-вызова, `const val` ребра не даёт вовсе. Для правила уровней это верное поведение
(важно, что реально импортируется), но «ребро исчезло» после пометки функции `inline` — не устранение.

**Оракул.** Тождество. **Приёмка.** Классов `…In` нет; поле стадии объявлено в одном месте (`dups.py` не находит
списков полей); `depgraph.py` — рёбер вверх нет, список известных пуст, цикл распался до пар внутри одного уровня
либо исчез; правило «Как менять» о передаче величин между стадиями в `docs/pain-and-gain.md` переписано под новую
форму; таблица уровней сверена с фактическим графом, отличия от стартовой возвращены оператору.

### Этап 6. Счётчики — к владельцам

**Что делается.** Каждое из 240 объявлений `Instruments.kt` получает владельца — стадию, которая его пишет
(`grep` по сеттерам; граф приложения Б даёт список по файлам) — и переезжает в её файл. Счётчик, который пишут две
стадии, — находка: либо у него есть владелец и второй писатель ошибочен, либо это две величины под одним именем.
`Instruments.printTick` и остальные печати читают счётчики у владельцев; текст строк не меняется. Сброс и починка
после оборванного тика — как сегодня (проверить, что `AbortRepair` видит новые места: простые `var` верхнего уровня
он не чинит и сегодня, словари и множества — только в объектах-владельцах).

**Оракул.** Тождество. **Приёмка.** В графе ни одна стадия не импортирует `Instruments`; раздел «Архитектура» в
`docs/pain-and-gain.md` переписан: правило о доме счётчика — новое.

### Этап 7. Удаление доказанно мёртвого (идёт параллельно, начиная с конца этапа 3)

**Кандидаты** дают приборы: `true = 0` и `won = 0` на гейте и живых сериях; строки «не исполнено» и «не целиком» из
`reach.py`.

**Удаляется только доказанное**, одно из двух:

- **перекрытие порядком:** условие строки влечёт условие строки выше — показывается чтением (логическое следствие
  выписывается в сообщении коммита), счётчик `shadowed = true` — свидетельство, а не доказательство;
- **невозможное условие:** конъюнкт, ложный по построению данных (величина, которую никто не пишет; состояние,
  в которое нет перехода).

Всё остальное — «редкое», а не «мёртвое», и остаётся (решение оператора 10). Список редкого со счётчиками —
со стенда сразу, живые счётчики после итоговой серии — **возвращается оператору находкой**: убрать редкую ветку —
решение о поведении, не уборка.

**Оракул.** Тождество (удаление недостижимого логи не меняет) + `verdicts.py check`: вердикты удалённых веток
уезжают в `docs/`.

## 6. Проверка

### 6.1. Тождество (каждый коммит этапов 1–7)

```shell
zsh tools/stub/painandgain/regress.sh land > gate_new.txt
python3 tools/stub/painandgain/compare.py runs/gate_<эталон>.txt gate_new.txt     # «без изменений» по всем строкам
python3 tools/stub/painandgain/logdiff.py --old runs/gate_<эталон> --new tools/stub/painandgain/out   # 0 расхождений
python3 tools/stub/painandgain/verdicts.py check                                  # 0 пропаж
```

Логи сценариев детерминированы, кроме `cpu t=` и `time=`; `logdiff.py` уже отбрасывает их и строки `tac t=`.
Новое поле прибора — новая маска в `logdiff.py`; **существующие поля не маскируются никогда** — это и есть оракул.
Эталон снимается один раз, с коммита, от которого стартует план, и держится до конца: поведенческих версий между
шагами нет (раздел 7). Если оператор всё же вставит такую версию передачей пакета, эталон переснимается с неё.

⚠️ **У детерминизма стенда есть условие: предохранители CPU молчат.** Они читают настоящее время, и на загруженной
машине (параллельные сессии, сбор покрытия) тик может перевалить за `CPU_GUARD_MS` — тогда бот законно ведёт себя
иначе, и расхождение логов будет **не ошибкой переноса**. Поэтому: в эталоне и в каждом новом прогоне число строк
`guard:` равно нулю (сегодня в 270 логах гейта их ноль), а при любом расхождении `logdiff.py` первым делом
проверяется именно это. Если переработка сама сделала тик настолько дороже, что предохранитель заговорил на
стенде, — это находка о CPU, а не шум, и она останавливает этап.

### 6.2. Сила оракула

`reach.py` на полном гейте перед каждым из этапов 3 и 4 и после него: множество исполненных строк переносимой
функции не уменьшилось (в пересчёте на новые места). Строка вне покрытия — правило 3.3.

### 6.3. CPU — один раз, после всего плана, в рейтинговой серии (решение оператора 12)

Таблицы лямбд, объекты `Turn` / `Aim` и полный обход условий — новая нагрузка; носители вместо замыканий и кэш
`Unit` вместо сканов `creep.body` — снятая; знак суммы заранее неизвестен. Живой замер делается один раз — на
итоговой серии (6.4), отдельных серий под CPU нет.

- **Контроль уже лежит в хранилище**: матчи версии, с которой стартует план (на 19.09.2026 — по десять матчей v438
  и v439). Бот сам печатает то, что нужно (`Instruments.kt:163–172`): каждые сто тиков `cpu t=N: max=…ms at t=M
  slow(>60ms)=K limit=100/1000ms`, а на тиках 1–3, на каждом тике дольше `CPU_SLOW_MS` и каждые сто тиков — разбивку
  по фазам `cpu t=N total=…ms: fields=… built=… posture=… command=… moves=… shoot=… resolve=…`.
- ⚠️ **CPU здесь — не только бюджет, но и вход поведения.** В коде три предохранителя, которые под нехваткой времени
  меняют решение: бегуны держат флаги (`Missions.kt:126`), командир пропускает перебор (`Strategist.kt:1408`),
  постура держит цель (`Strategist.kt:2197`); каждый печатает `cpu t=N guard: …`. Тождество на стенде их не видит —
  там времени хватает всегда. Поэтому число строк `guard:` на матч у итоговой версии сравнивается с контролем тем же
  способом: выросло — переработка изменила поведение живьём **через CPU**, хотя логика тождественна.
- **«Не хуже»** — `max=` по окнам и счёт `slow(>60ms)=` итоговой версии лежат внутри разброса, который контрольная
  версия показывает **между своими же матчами**; ни одного `Script execution timed out`. Порог берётся из разброса
  контроля, а не называется. Особое внимание тикам 2–35: по прошлому плану там 60–95 мс из 100.
- **Если хуже — виновного называет разбивка по фазам**, а не догадка: `fields` / `built` — этап 1 (кэш `Unit` в
  `buildWorld`), `moves` — этапы 2–3 (`creepTurn`, таблицы, полный обход), `command` — этап 4 (`commandFight`),
  `posture` — этап 4 (`armyStrategy`, `captureAllowed`). Первое средство — рубильник полного обхода (4.3), слово за
  оператором; дальше — теги этапов и бесплатные тестовые игры (`tools/play.py --test`) на теге до и после
  подозреваемого этапа.
- **След на стенде — бесплатный побочный продукт гейта**: раннер печатает `cpu t=N: max=..ms … slow(>50ms)=K` каждые
  сто тиков. Абсолютные числа стенда к живой VM не относятся (по прошлому плану расхождение ×8), но сдвиг от этапа к
  этапу на одной машине виден. После каждого этапа в абзац версии пишется сумма `slow` и наибольший `max` по логам
  гейта до и после — чтобы при провале итогового замера было с чем сверить разбивку по фазам. Вердикта этот след не
  выносит.

### 6.4. Итоговая живая проверка — после всего плана (решение оператора 11)

Рейтинговых игр до конца плана нет. Когда этапы 0–7 посажены, исполнитель докладывает оператору (раздел 10) и **по
его слову** играет рейтинговую серию; размер серии называет оператор (в проекте принята серия из двадцати). Серия
отвечает на один вопрос — не разошлось ли тождество на стенде с жизнью:

- CPU — по 6.3;
- распределения приборов против контрольной версии, **по ботам соперника, а не по игрокам**
  (`tools/series.py compare <стартовая> <итоговая>`, `metrics`): доли `rung` / `step` / `pass`, постуры, `cmdwhy`.
  Первыми смотрятся строки, помеченные в абзацах версий «стендом не исполняется» (3.3);
- исход серии (побед-поражений, рейтинг) **описывает, а не решает**: жеребьёвка соперников шумнее любого эффекта
  переработки — так же читалась серия v263;
- новые счётчики `reach` дают живой список «редкого» и кандидатов этапа 7 — он уходит оператору.

Нашлось расхождение — виновный этап ищется по тегам бесплатными тестовыми играми, откат — к тегу последнего этапа,
который проверку проходит; что делать дальше, решает оператор.

## 7. Организация работ

- **Кто.** Отдельная сессия-разработчик (решение оператора 2), весь план одной задачей (решение 3).
- **Где.** Ворктри арены `.claude/worktrees/pain-and-gain`, ветка `pain-and-gain` («one arena, one worktree» в
  `CLAUDE.md`): на него смотрит симлинк клиента, в нём лежат эталоны `runs/` и логи `out/`. Этот файл лежит на ветке
  `pain-and-gain-architecture` (один коммит поверх `cf4fa56`) и забирается в ветку бота
  `git cherry-pick pain-and-gain-architecture`.
- ⚠️ **Предусловие старта — пакет свободен.** 19.09.2026 в этом ворктри работала поведенческая сессия: пока
  писался план, вышли v439 и v440. Этапы 1–6 переписывают почти каждый файл пакета, а у файла в один момент один
  пишущий, поэтому до старта оператор останавливает поведенческую сессию либо уводит её с пакета, а разработчик
  проверяет это сам: `git status --short` пуст (кроме `runs/` и `.claude/`), `git log -1` не движется, работа той
  сессии посажена или хотя бы закоммичена. **Этап 0 — единственный, кому пакет не нужен** (он правит только
  `tools/`), и его можно начать раньше, в своём ворктри от `main`.
- **Поведенческая версия посреди плана — только передачей пакета целиком:** разработчик доводит текущий шаг до
  посадки и говорит «отдал»; та сессия делает `git rebase main`, свою версию, сажает и говорит «вернул»;
  разработчик делает `git rebase main`, **переснимает эталон** и продолжает. Единица передачи — пакет, а не файл и
  не задача. По умолчанию таких вставок нет.
- **Версии.** `BOT_VERSION` поднимается на каждую посадку, как принято; абзац версии в `docs/pain-and-gain.md`
  говорит «тождество» и называет этап.
- **Общее.** `tools/depgraph.py` и правки под `tools/` — отдельными коммитами и в `main` сразу (правило 5 из
  `CLAUDE.md`); `types/`, Gradle, `arenas/`, `land.sh` не трогаются.
- **Документы.** После каждого этапа — раздел «Архитектура» в `docs/pain-and-gain.md`: таблица файлов и правила
  «Как менять» (этапы 1, 5, 6 их меняют). Карты секций этапа 4 — отдельным файлом в `docs/`.
- **Порядок.** 0 → 1 → 2 → 3 → 4 → 5 → 6; этап 7 — рядом, начиная с конца 3. Этапы 5 и 6 независимы друг от
  друга. Живых игр — ни рейтинговых, ни под CPU — до конца плана нет (решения 11 и 12).
- **Сверх плана исполнитель не чинит.** Дефект поведения, замеченный при переносе (а их будет видно много — код
  впервые читается целиком), переносится **как есть**, тождественно, и возвращается оператору находкой с местом и
  описанием. Починка на месте ломает оракул, которым проверяется всё остальное.

## 8. Чего в плане нет — и почему

- **Клетка как argmax списка термов, единая модель строя, `Disposition` как решатель, назначение огня отрядом,
  спасение первым в арбитре.** Это смены поведения; первые попытки отвергнуты живым A/B (v242, v244, v246, v253).
  После этапов 3–4 каждая из них становится правкой одной таблицы или одного метода и может быть предложена заново,
  отдельной версией, со своим A/B.
- **Нормализация форматов приборов** (`k=v` на каждый счётчик) — ломает тождество логов и сопоставимость
  `series.py` с v2xx–v4xx.
- **Сведение написаний А и Б** «чистого мили» — решение о поведении (правило 3.4).
- **Новый бот рядом** — решение оператора от 13.09.2026.
- **Внешний просмотрщик архитектуры** (`unclebob/uml-viewer`): разбирает только Clojure, пакет плоский, метрики
  цвета для Kotlin/JS взять неоткуда; то, что он показал бы, даёт `depgraph.py` — и с именами символов на рёбрах,
  которых у него нет.

## 9. Решения оператора (19.09.2026)

1. **План утверждён без изменений** — вместе с рамкой (ни один шаг не меняет поведение, каждый проверяется
   тождеством, механика и поведение не делят коммит) и с тем, чего в нём нет (раздел 8).
2. **Исполняет отдельная сессия-разработчик**, не поведенческая сессия арены. Следствие — предусловие «пакет
   свободен» и передача пакета целиком (раздел 7).
3. **План отдаётся целиком, одной задачей** — этапы 0–7 по порядку, без промежуточных постановок.
4. **Правило «счётчик, который только печатается, — в `Instruments.kt`» отменено**: счётчик живёт у стадии,
   которая его считает (4.7, этап 6).
5. **Классы `…In` убираются**: правило «оркестровка распаковывает выход в локальные с прежними именами» отменено,
   стадия получает выходы предыдущих целиком (4.5, этап 5). Цена — сотни механических замен — названа и принята.
6. **Таблица уровней (4.6) принята как стартовая**, включая модель мощи уровнем ниже `World` и `Instruments` вне
   уровней; пересмотр — на этапе 5, отличия возвращаются оператору.
7. **Линт написаний и гейт графа блокируют посадку** (этап 0).
8. **Полный обход условий со счётчиками `true` / `shadowed` включён в живой сборке** (4.3); цена входит в итоговый
   замер CPU, рубильник остаётся константой сборки, выключение — слово оператора.
9. **Написания А и Б «чистого мили» в этом плане не сводятся**; после этапа 1 оператору возвращается таблица по 27
   местам, сведение — отдельная поведенческая версия после плана.
10. **Редкие ветки остаются**; без слова оператора удаляется только доказанно недостижимое (этап 7), список редкого
    со счётчиками возвращается оператору.
11. **Рейтинговые игры — только после выполнения всего плана** (6.4), по слову оператора.
12. **CPU меряется после всего плана, в рамках тех же рейтинговых игр** (6.3); отдельных серий под CPU нет, контроль —
    матчи стартовой версии из хранилища.
13. **Строки, которых стенд не исполняет, читает второй агент** — свежий субагент без контекста автора (3.3).

**Что возвращается оператору по ходу** (находки, а не вопросы — работу они не останавливают):

| когда | что |

## Приложение А. Прототип `reach.py` (проверен 19.09.2026)

Покрытие снимается без правки бота и стенда: `NODE_V8_COVERAGE=<каталог>` перед запуском сценариев, каждый процесс
`node` кладёт туда свой JSON. Прототип сливает их (максимум счётчика по диапазону), красит символы
скомпилированного `.mjs` «исполнено / не исполнено» (вложенные диапазоны поверх внешних) и переводит отрезки в
строки Kotlin через `.mjs.map` соседнего файла. Сборка `per-file` даёт по модулю на файл `.kt`, отрезки, пришедшие
инлайном из stdlib и чужих файлов, отбрасываются. Три сценария — ~100 с; запускался с копии стенда вне ворктри,
бот подставлялся переменной `BOT=file://…/PainAndGain.export.mjs`.

<details><summary>reach.py</summary>

```python
#!/usr/bin/env python3
"""Покрытие V8 (каталог NODE_V8_COVERAGE) -> строки Kotlin пакета, которые гейт ни разу не исполнил.
   python3 reach.py <каталог-покрытия> [Файл.kt:от-до ...]"""
import collections, glob, json, os, sys
PKG = '/season4/painandgain/'
B64 = {c: i for i, c in enumerate('ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/')}

def vlq(seg):
    out, shift, val = [], 0, 0
    for ch in seg:
        d = B64[ch]; val |= (d & 31) << shift; shift += 5
        if not d & 32:
            out.append(-(val >> 1) if val & 1 else val >> 1); shift = val = 0
    return out

blocks = collections.defaultdict(dict)                     # url -> {(start, end): max count по всем процессам}
for f in glob.glob(os.path.join(sys.argv[1], '*.json')):
    for e in json.load(open(f))['result']:
        if PKG not in e['url'] or e['url'].endswith('.export.mjs'): continue
        for fn in e['functions']:
            for r in fn['ranges']:
                k = (r['startOffset'], r['endOffset'])
                blocks[e['url']][k] = max(blocks[e['url']].get(k, 0), r['count'])

seen, hit, part = (collections.defaultdict(set) for _ in range(3))
for url, bl in blocks.items():
    path = url.replace('file://', '')
    text = open(path, encoding='utf-8').read()
    mask = bytearray(len(text) + 1)                        # 0 верх модуля, 1 исполнено, 2 не исполнено
    for (a, b), c in sorted(bl.items(), key=lambda x: (x[0][0], -x[0][1])):   # внешние диапазоны раньше вложенных
        mask[a:b] = bytes([1 if c > 0 else 2]) * (b - a)
    starts = [0] + [i + 1 for i, ch in enumerate(text) if ch == '\n']
    sm = json.load(open(path + '.map'))
    names = [os.path.basename(s) for s in sm['sources']]
    own = os.path.basename(path).replace('.mjs', '.kt')
    si = sl = 0
    for gl, line in enumerate(sm['mappings'].split(';')):
        gc, segs = 0, []
        for seg in filter(None, line.split(',')):
            v = vlq(seg); gc += v[0]
            if len(v) >= 4: si += v[1]; sl += v[2]; segs.append((gc, si, sl))
        end = starts[gl + 1] - 1 if gl + 1 < len(starts) else len(text)
        for j, (c0, s, l) in enumerate(segs):
            if names[s] != own: continue                   # инлайн из stdlib и чужих файлов — не наш код
            a = starts[gl] + c0
            b = max(a + 1, starts[gl] + segs[j + 1][0] if j + 1 < len(segs) else end)
            seen[own].add(l + 1)
            if any(m != 2 for m in mask[a:b]): hit[own].add(l + 1)
            if any(m == 2 for m in mask[a:b]): part[own].add(l + 1)

N = M = P = 0
for f in sorted(seen):
    never, partial = seen[f] - hit[f], part[f] & hit[f]
    N += len(seen[f]); M += len(never); P += len(partial)
    print('%-18s строк кода %5d  не исполнено %4d (%4.1f%%)  исполнено не целиком %4d'
          % (f, len(seen[f]), len(never), 100.0 * len(never) / len(seen[f]), len(partial)))
print('ИТОГО              строк кода %5d  не исполнено %4d (%4.1f%%)  исполнено не целиком %4d (%4.1f%%)'
      % (N, M, 100.0 * M / N, P, 100.0 * P / N))
for w in sys.argv[2:]:                                     # окно «Файл.kt:от-до» — номера строк для чтения глазами
    f, r = w.split(':'); a, b = map(int, r.split('-'))
    print(w, 'не исполнено:', sorted(l for l in seen[f] - hit[f] if a <= l <= b))
    print(w, 'не целиком:  ', sorted(l for l in part[f] & hit[f] if a <= l <= b))
```

Оговорки прототипа: смещения V8 — в единицах UTF-16, прототип считает символами Python (расходится только на

## Приложение Б. Прототип `depgraph.py` (проверен 19.09.2026)

Граф не выводится из Kotlin — в плоском пакете импортов между файлами нет. Он читается из результата компиляции:
`kotlin.js.ir.output.granularity=per-file` даёт модуль на файл с настоящими `import { … } from './World.mjs'`,
разрешёнными компилятором, вместе с именами символов.

<details><summary>depgraph.py</summary>

```python
#!/usr/bin/env python3
"""python3 depgraph.py build/js/packages/screeps-kotlin-arena-starter/kotlin/screeps-kotlin-arena-starter/season4/painandgain"""
import collections, os, re, sys
D = sys.argv[1]
files = sorted(f[:-4] for f in os.listdir(D) if f.endswith('.mjs') and not f.endswith('.export.mjs'))
imp = re.compile(r"import\s*\{([^}]*)\}\s*from\s*'\./([A-Za-z]+)\.mjs'", re.S)
E = collections.defaultdict(lambda: collections.defaultdict(list))        # откуда -> куда -> [символы]
for f in files:
    for names, to in imp.findall(open(os.path.join(D, f + '.mjs')).read()):
        if to != f and to in files:
            E[f][to] += [n.split(' as ')[-1].strip() for n in names.split(',') if n.strip()]

w = max(map(len, files))
print(' ' * w, ' '.join(f[:3] for f in files))
for f in files:
    print(f.ljust(w), ' '.join((str(len(E[f][t])) if E[f].get(t) else '\\' if t == f else '').rjust(3) for t in files))
print('рёбер', sum(len(v) for v in E.values()), 'символов', sum(len(s) for v in E.values() for s in v.values()))

idx, low, st, on, comps, c = {}, {}, [], set(), [], [0]                   # Тарьян
def sc(v):
    idx[v] = low[v] = c[0]; c[0] += 1; st.append(v); on.add(v)
    for t in E[v]:
        if t not in idx: sc(t); low[v] = min(low[v], low[t])
        elif t in on: low[v] = min(low[v], idx[t])
    if low[v] == idx[v]:
        comp = []
        while True:
            x = st.pop(); on.discard(x); comp.append(x)
            if x == v: break
        comps.append(sorted(comp))
for f in files:
    if f not in idx: sc(f)
for comp in sorted(comps, key=len, reverse=True):
    if len(comp) > 1: print('цикл на', len(comp), ':', ', '.join(comp))
for a, b in (p.split('>') for p in sys.argv[2:]):                         # «World>Strategist» — символы на ребре
    print(a, '->', b, len(E[a][b]), ':', ', '.join(E[a][b][:20]))
```
